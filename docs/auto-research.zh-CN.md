## 每次巡检

用户另行授权评价加速与分层诊断升级；活动目录可能切换至 `feedback10-evaluation-v2`。详见 [v2 评价与恢复合同](evaluation-v2.zh-CN.md)。完整旧轮次保留旧评价；升级时未完成轮次复用原始生成结果，按新政策统一复评。PLIP 未抽中、化学无效或结构失败的亲和力跳过均不是技术缺失，不可补零；核心技术错误仍暂停。本次升级不属于 auto research 新周期。

“唯一执行进程”指唯一实验主进程；配置中的 CPU 工作子进程属于同一运行。v2 停机或恢复时也要核验其进程组，不能让旧工作进程继续写入旧目录后又启动重复评价。CPU 评价检查点用于恢复，但不能替代最终含亲和力状态的 `evaluation.json`；轮次完成仍以全部最终报告为准。

1. 阅读活动登记与上次巡检报告，检查对应进程确实仍是实验进程，不能仅凭 PID 存在判断。使用 `scripts/inspect_run.py --run-dir <目录> --pid <PID> --output <巡检 JSON>` 获取只读快照。检查原始日志时只返回必要诊断，不输出环境变量或凭据。
2. 按教师汇报：已完成轮数、当前阶段、生成数、评价数、各类失败数、结构合格数、近期产物时间。生成与评价是两个屏障，不能把已生成数量称为已完成评价。规划 API 正在工作时，候选数量暂时不变并不代表停滞。
3. 查看异常和磁盘空间；若产物长时间不变，结合进程 CPU/GPU、日志和上次快照定位。评价技术异常是缺失，化学无效或生成失败是保留在分母内的有效反馈。不得填造零分，不得补足成功样本而重采样。
4. 如进程已停止，先确认是否正常完成；否则保存故障证据。仅对已定位、可恢复的环境或服务故障恢复同一配置。恢复前核对源码、权重、配置与评价合同；使用唯一运行锁，确认没有同目录活跃任务。保留既有候选与冻结路径。新启动使用新日志文件，不能覆盖旧日志。
5. API 有限重试失败、规划修订仍无效或代码错误需要独立诊断；不可用反复重启绕过原先的有限修订预算。需要改动算法时使用新版本和新运行目录，并明确原运行未完成。若仅修复技术性表示校验，可在对全部已有结果和教师条件完成无变化审计后，用显式谱系迁移继续；详见 [首次 PLIP 修复](repair-20261027.zh-CN.md)。不得直接修改旧 `run.json` 绕过合同。
6. 保存带时间戳的 JSON 快照和简短巡检说明。每两小时向用户汇报一次；若无法连接，明确本次未取得远端最新状态，不能把上次观察当作最新进度。

## 完整实验结束判据

必须核对两位教师的基线、全部 10 轮和每轮全部 5 条路径，每条路径的所有尝试都有明确生成与评价记录。各阶段 `complete.json` 和最终 `final.json` 必须与候选计数一致。若有合格搜索路径，赢家与静态基线均须完成独立确认；若没有合格路径，明确保存失败结果并记录不执行确认的原因。此时实际次数可以少于最大预算。

`status.json` 的 `complete` 不能单独作为充分证据；只读巡检器同时核对完成标记与计数。它不替代源码哈希、输出来源哈希及恢复时的正式一致性校验。`interface-feedback` 等小规模接口验证不是完整正式实验。只有完整实验通过上述核算，才进入下一周期的 auto research。
